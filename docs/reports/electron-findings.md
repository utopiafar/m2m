# Electron 与复杂场景验证报告

本文档记录对 **Electron（Chromium）目标应用**的实测结论，以及为支持这类应用所做的
实现变更。全部结论来自真机实测，不是文档推断。

验证对象：

| 对象 | 说明 |
|---|---|
| 自建 Electron demo（`TestApps/electron-demo`） | 含 `contenteditable` 聊天输入、原生 `textarea`、虚拟滚动列表、设置窗口、模态对话框；开启 `--force-renderer-accessibility` |
| **Visual Studio Code 1.139**（真实第三方 Electron 应用） | 用于验证结论在真实应用上是否成立，而不是只在我的 demo 上成立 |
| 原生 AppKit demo（对照组） | 作为"通用 AX 路径本应达到什么水平"的基线 |

---

## 一、结论速览

| 能力 | 原生 AppKit | Electron / Chromium |
|---|---|---|
| 窗口枚举（AX/CG） | ✅ | ✅ 需先启用无障碍树 |
| 改窗口尺寸 | ✅ | ✅ 需先启用无障碍树 |
| 读到编辑控件 | ✅ `AXTextArea` | ✅ `AXTextArea`（`contenteditable` 与 `textarea` 都暴露） |
| 读到控件文本内容 | ✅ `AXValue` | ❌ 不暴露 `AXValue` |
| **读到可用的插入点矩形** | ✅ `(73, 434, 0×18)` | ❌ 返回 `(0, 956, 0×0)` —— **不可用** |
| 写入文字 | ✅ AX 选区写入 | ⚠️ AX 选区写入**返回成功但不生效**；CGEvent Unicode 注入生效 |
| 写入结果校验 | ✅ 可读回校验 | ❌ 无法程序化校验 |
| 是否达到「本地输入法体验达标」（P2） | ✅ 是 | ❌ **否**，如实判定为「候选窗位置近似」 |

**一句话**：Electron 应用**能读控件、能写文字**，但**读不到可用的插入点**，
因此本地输入法候选窗无法精确跟随光标——按项目已定的规则（P2），
这类应用**不得**被标注为"本地输入法体验达标"，只能如实降级。

## 二、支撑证据

### 1. Chromium 默认不构建无障碍树

未做任何处理时，VS Code 的 AX 侧**一个控件都没有**：`kAXWindowsAttribute` 为空、
焦点控件读不到。窗口能枚举到（来自 CG），但 AX 完全不可用。

实现上补了显式激活（`AXAccessibilityEnabler`）：设置 `AXManualAccessibility`
（Electron 官方文档提到的第三方启用方式）与 `AXEnhancedUserInterface`，
然后轮询等待树可用。

- 自建 demo 用命令行开关 `--force-renderer-accessibility` 可稳定启用
- VS Code 需要同样开启该开关后才暴露控件

**这是 Electron 目标的第一个前置条件：应用必须暴露无障碍树。**

### 2. 插入点矩形"可读 ≠ 可用"

Chromium 把 `contenteditable` 正确暴露为 `AXTextArea`（连 `aria-label` 都在），
`kAXBoundsForRangeParameterizedAttribute` 也能调用成功——**返回的矩形是 `0x0`**。

对照组：原生 AppKit 文本框返回 `0×18`（零宽竖条，这正是文本光标的形态）。

因此实现了明确的可用性校验：

| 返回 | 判定 | 理由 |
|---|---|---|
| `0×18` | ✅ 可用 | 零宽竖条是文本光标的正常形态 |
| `0×0` | ❌ 不可用 | 没有位置信息 |
| 落在窗口之外 | ❌ 不可用 | 不是"光标位置" |

没有这道校验时，界面会声称"光标跟随"，而候选窗实际会出现在屏幕上一个
毫不相干的位置——比明确降级更糟。

### 3. AX 写入"返回成功但不生效"

Chromium 对 `AXUIElementSetAttributeValue(…, kAXSelectedTextAttribute, …)`
返回 `.success`，但控件内容**毫无变化**。这是最危险的一类失败：不报错。

因此提交执行器改为**两条路径 + 读回校验**：

1. AX 选区写入 → 读回比对
2. CGEvent Unicode 注入（真实用户按键走的通道）→ 读回比对
3. 两者都无法确认时……

### 4. 由此引入的第三种提交状态

Chromium 不暴露 `AXValue`，所以第 2 条路径**确实生效**（实测 DOM 文本变成了
`你好，Electron`）但**无法校验**。

把它判为"已生效"是谎报，判为"不支持"是误报。因此协议新增第三态：

```swift
case appliedUnverified = 6   // 已执行，但目标控件不提供可读内容，无法校验
```

它属于 `isApplied`（流程继续、版本推进），但界面会明确提示
"该应用不支持输入结果校验"。这与既有状态是并列关系：

| 状态 | 含义 |
|---|---|
| `applied` | 已执行并**校验通过** |
| `appliedUnverified` | **已执行，无法校验**（Chromium 系） |
| `rejectedUnsupported` | 有证据表明未生效 |
| `unknown` | 结果不明，等待重新同步 |

## 三、对目标应用（如果它是 Electron）的含义

原始需求的目标是官方 Claude 桌面客户端，公开资料显示它是 Electron 应用。
基于本次实测，可以给出明确判断：

1. **画面、窗口、缩放**：可行。Chromium 启用无障碍树后窗口操作完全可用。
2. **文字输入**：可行，走 CGEvent Unicode 通道；但输入结果**无法程序化校验**。
3. **候选窗精确跟随光标**：**不可行**（通用 AX 路径下）。Chromium 不提供可用的
   插入点几何。这与前期调研的 R2 风险判断一致，现在有了硬证据。
4. **因此**：按 P2 规则，该目标会落在**降级模式**——可用，但不得宣称"原生输入法体验"。

要达到"光标跟随"只有两条路，都超出"不改包、不注入"的一期范围：

- **应用专用适配器**：通过 Chromium 的调试协议（CDP 的 `imeSetComposition` 等）
  或 Electron 的应用内接口获取/注入编辑状态。需要应用开放入口，且随版本维护。
- **应用侧配合**：让目标应用自行暴露符合需要的 AX 信息。

## 四、这一轮修掉/新增的实现

| 变更 | 原因 |
|---|---|
| `AXAccessibilityEnabler` | Electron 默认不建无障碍树；"窗口非空"不足以判定可用，改判"有有效窗口尺寸或焦点控件可读" |
| 焦点控件查找分三级 + 容器下探 | Chromium 在应用/窗口级返回的是 `AXWebArea` 容器，真正控件在其子树 |
| 插入点矩形可用性校验 | 杜绝"读得到但不可用"（`0x0`）冒充"光标跟随" |
| 提交读回校验 + `appliedUnverified` | 避免"API 返回成功"被当成"输入成功" |
| 能力运行时更新（`capabilityUpdate`） | 能力只在握手时下发会导致长期显示过期的降级/达标状态 |
| 输入按会话就绪门控 | 重连期间发出的输入会被按过期代次丢弃，静默丢字 |
| Electron 辅助进程清理 | 主进程退出后 renderer/GPU 进程仍占用屏幕录制与辅助功能资源，批量跑场景时累积成假故障 |

## 五、环境限制（诚实边界）

- **Chromium 的焦点控件读取要求目标应用处于前台**，而**后台进程无法强制激活
  另一个应用**（实测 `NSRunningApplication.activate` 返回 `false`）。
  专用远端机上应用本就应是前台应用，因此真实部署不受影响；
  但在自动化环境里这构成前置条件——`electron-focus` 场景在不满足时标记为**跳过**
  （跳过既不算通过也不算失败）。
- **批量连续运行 GUI 场景**（14 个场景背靠背）会因共享同一个图形会话与
  屏幕录制/辅助功能资源而互相干扰：**单独运行全部通过，批量运行约 12–14/14**。
  这不是产品缺陷，但说明这套 GUI 场景不适合作为高频回归；建议按需单独运行。
- VS Code 属于自绘编辑器（Monaco），其 AX 暴露程度低于基于标准 DOM 控件的
  应用。自建 demo 的 `contenteditable` 暴露更完整。不同 Electron 应用之间仍有差异，
  需要按目标应用单独验证。
