# 05 媒体与性能

## 1. 先接受一个不能绕过的下限

```
操作到画面反馈 ≈ 网络往返 + 远端处理 + 采集编码 + 解码显示 + 排队
```

调研给出的算例（后几项合计约 30 ms）：

| 实际通信路径 RTT | 操作反馈算例 |
|---:|---:|
| 20 ms | 约 50 ms |
| 80 ms | 约 110 ms |
| 160 ms | 约 190 ms |
| 250 ms | 约 280 ms |

**这是原理算例，不是实测。**

结论：切换 UI 传输方式**不能**让远端按钮在 20 ms 内完成真实反馈。分层架构的价值在于让**窗口拖动、本地光标、候选词**不受 RTT 影响。

## 2. 链路

```
远端 Claude 窗口
  → ScreenCaptureKit（按窗口过滤，GPU 内存缓冲）
  → VideoToolbox 实时低延迟编码（消除帧重排序）
  → WebRTC（直连优先，失败走 TURN）
  → 本地硬件解码
  → CAMetalLayer 显示层
```

Apple 提供的能力：ScreenCaptureKit 提供窗口/应用过滤、GPU 支持缓冲、动态分辨率与帧率配置、无变化帧状态；VideoToolbox 有面向实时通信的低延迟模式，明确消除帧重排序，并支持通过画质约束在弱网下牺牲部分帧率、保留清晰屏幕内容。

**但这些"低延迟"不能直接推导出跨境实测结果。** H.264/HEVC、色彩格式、编码档位必须在两台机器上实测（G3）。

## 3. 采集策略（T5：主窗口独立流）

| 项 | 一期选择 |
|---|---|
| 主窗口 | **每个窗口一条独立媒体流**（独立分辨率、独立降频） |
| 活跃窗口数 | 限制（建议 ≤ 3 条同时活跃流）；后台窗口降频或暂停 |
| 弹窗/子窗口 | **不机械地各开一个编码器**：`includeChildWindows` 已可包含，但采集到 ≠ 父子/位置/模态已解决 |
| 图集方案 | **一期不使用**；仅当 G2/G3 实测证明多窗口编码压力或弹窗兼容性更优时再引入 |
| 最小化窗口 | 停止编码，发 `StreamState.paused`（不持续发同一帧）；恢复先发关键帧 |

### 为什么不一期就用图集

图集（虚拟显示器平铺 + 一条采集流 + 客户端取区域）能减少链路数量，但代价是：排列窗口、处理弹窗越界、同步区域元数据、限制总像素量。**对 1–3 个主窗口的场景，先按实测决定，而不是先认为其中一种必然更快。**

若采用图集，两条不可妥协的约束（一期若启用则为强制项）：

1. **过滤必须发生在远端编码之前**。不得把含其他应用和通知的完整画布发到本地、只在客户端不显示。
2. **画面与窗口区域元数据必须对应同一 `layout_version`**。

## 4. 排队控制（比峰值帧率更重要）

| 规则 | 原因 |
|---|---|
| 输入控制消息优先，不被文件上传阻塞 | 避免"上传文件时点击失灵" |
| 采集与编码队列保持有界 | 防止内存增长与延迟累积 |
| 后台窗口降频 | 节省 CPU/GPU/带宽 |
| 重连立即请求可解码关键帧 | 避免长时间等待下一个 IIDR |
| 可丢弃**尚未编码**的过期画面 | 优先显示最新画面 |
| **不得**无视参考依赖丢弃**已编码**帧 | 会花屏并触发整帧重传，反而放大延迟 |
| 使用实时编码模式，不为压缩率积累额外帧 | VideoToolbox 低延迟模式即为此设计 |

这些不是为了提高跑分，而是避免"网络偶尔卡一下，随后一直慢半秒"的累积延迟。

## 5. 尺寸与 Retina（T6：正确性要求）

### 5.1 四个必须区分的尺寸

| 概念 | 来源 |
|---|---|
| 本地逻辑点 | 本地 `NSWindow` contentRect |
| 本地像素 | 本地逻辑点 × 本地 backingScaleFactor |
| 远端逻辑点 | `WindowSnapshot.content_rect` |
| 远端采集像素 | `StreamInfo.content_size_px`（= 远端逻辑点 × `content_scale`） |

ScreenCaptureKit 的采集元数据提供 `contentRect`、`contentScale`、`scaleFactor`，正是处理这些映射的依据。

### 5.2 交互流程（必须实现，不得降级）

```
拖动缩放中：
  本地立即改变外框（本地 UI 线程，不等网络）
  暂时缩放旧画面显示
  远端尺寸请求按 ~10 Hz 合并发送（只发最新 request_seq）

拖动结束：
  提交最终尺寸
  远端重新排版并返回 WindowResizeResult.actual_content_size
  客户端切换到新尺寸的清晰画面
```

**判据**：拖动过程中短暂模糊可接受；**松手后仍然只是缩放旧分辨率 = 未实现**。

### 5.3 约束传递

应用可能限制最小尺寸，系统可能限制位置。规则：

- 本地**必须接受** `actual_content_size`，不得坚持请求值；
- 若应用拒绝缩放（`resizable=none`），本地应禁用缩放 UI，而不是允许拖动后才回弹；
- `constrained_by` 用于界面解释，例如"该窗口最小宽度受应用限制"。

## 6. 文字清晰度优先于压低码率

主要内容是聊天文字、代码、按钮，不是游戏。

| 原则 | 实现 |
|---|---|
| 采集尺寸与最终显示尺寸匹配 | 避免长期把低分辨率画面拉伸到 Retina 窗口 |
| 静止时保清晰 | 静态内容降低更新频率，不降分辨率 |
| 滚动时保流畅 | 提高帧率，可适度降质量 |
| 弱网降级顺序 | **先降帧率 → 再适度降画质 → 最后才考虑降分辨率**（P10） |
| 质量约束 | 编码器使用面向屏幕内容的画质约束，避免文字被糊掉 |

**H.264 vs HEVC（T4）**：H.264 硬件链路作为基线，HEVC 做对照测试；只有在你的两台机器、所选 SDK 和线路上确有画质/码率收益时才启用。

## 7. 传输（T3：原生 WebRTC + TURN）

### 7.1 两条路线，别混为一谈

| 路线 | 结构 | 何时用 |
|---|---|---|
| **A：原生 WebRTC + TURN** | 一对一；能直连直连，不能直连经 TURN 转发；自己管信令、配对、会话恢复 | **一期默认**（T3） |
| **B：LiveKit + SFU** | 两端连媒体服务器，服务器转发媒体 | 出现固定经服务器、多人观看、大量会话管理需求时 |

**注意**：TURN 是**中继**，不是图像处理服务器；不要为了"允许第三方中继"就强制所有连接走可能更差的路径，应比较实际质量。

### 7.2 不要因为重视性能就排除 WebRTC

> "WebRTC 天然固定增加 50–100 ms，所以必须自研 UDP" 不是可靠依据。

WebRTC 缓冲量受实现、目标缓冲与网络状态影响；规范提供 `jitterBufferTarget`，并明确说明它是目标而非硬性保证，实际延迟需通过统计指标观察。

实施顺序：**先用成熟实时传输栈，测清楚延迟花在哪里；只有确认某个具体环节成为瓶颈，才替换那个环节。** 从头写 UDP，省掉的可能是缓冲，重新承担的则是丢包恢复、拥塞控制、乱序、加密与弱网适配。

### 7.3 需要避免的常见 AI 生成错误

| 错误 | 后果 |
|---|---|
| 把整个画面硬编一次，再交给 SDK 编码一次 | 双倍 CPU/GPU，画质二次损失 |
| 丢弃已编码帧以"降低延迟" | 参考帧缺失 → 花屏 → 关键帧重传 → 延迟更大 |
| 用轮询定时器代替事件驱动采集 | 延迟与 CPU 双高 |
| 在采集回调里同步查询 AX 树 | 媒体快路径被非媒体操作阻塞 |

## 8. 弱网策略（P10 落地）

| 网络状况 | 动作 |
|---|---|
| 轻微抖动 | 保持分辨率，降低帧率 |
| 持续丢包 | 提高画质约束优先级（保文字），允许帧率下降 |
| 严重拥塞 | 暂停后台窗口流；用户应能感知"当前为低质量模式" |
| 完全中断 | 进入 `RECONNECTING`，画面冻结但保留最后帧 + 明确状态提示；**不重放输入** |

本地应有可见的质量指示（不打断操作），让用户知道当前是降级状态。

## 9. 性能验收的写法

调研要求：**用条件明确的表述，而不是"支持 60 fps"。**

### 9.1 基线条件（G3）

| 条件 | 值 |
|---|---|
| 设备 | 固定的两台 Apple Silicon Mac（型号、系统版本记录在案） |
| 活跃窗口 | **单活跃窗口** |
| 物理像素尺寸 | 固定（例如 1600×1000 px） |
| 色域 | SDR |
| 内容 | 一段可重复的 Claude 聊天场景 + 一段滚动文本场景 |
| 网络 | 局域网基线；跨境条件通过注入 80 ms / 160 ms RTT 与丢包模拟 |

### 9.2 待验证的工程目标（不是已有框架的保证）

| 指标 | 目标 |
|---|---|
| 本地交互反馈（窗口移动、组合输入） | p95 ≤ 30 ms，**与网络无关** |
| 局域网远程操作到画面反馈 | 数十毫秒量级（中位数） |
| 阶段耗时 | 分别记录：采集、编码、传输、解码、显示、排队各自的耗时与中位数/较差值 |
| 文字质量 | 常用字号清晰；缩放停止后恢复清晰 |
| 延迟稳定性 | 连续操作 10 分钟后，延迟不出现单调累积 |

### 9.3 测量纪律

- **不要把不同测试里的 p95 简单相减**，宣称得到某模块的"精确耗时"。
- 不要用 ping 或厂商宣传的"低于 100 ms"替代端到端测量。
- 必须同时记录：远端主机 CPU/GPU、上行带宽占用、丢包率、断线次数。

## 10. 带宽与成本测算（供 08 引用）

假设：每天 4 小时、每月 22 天、共 88 小时，全部画面经中继。

```
月视频流量 ≈ 平均码率(Mbps) × 0.45 × 使用小时数
```

| 平均码率 | 视频本体 | 预留 20% 开销 |
|---:|---:|---:|
| 3 Mbps | 约 119 GB/月 | 约 143 GB/月 |
| 8 Mbps | 约 317 GB/月 | 约 380 GB/月 |
| 15 Mbps | 约 594 GB/月 | 约 713 GB/月 |

**这些是测算情景，不是 Claude 实测码率。** 真实值取决于分辨率、画质、滚动频率、窗口数量与编码策略——由 G3 给出。
