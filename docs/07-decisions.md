# 07 决策登记表

**本表的用途**：把前期调研中已经给出的建议值固化下来，避免开发过程中反复讨论已经定过的事。

**状态说明**：

| 状态 | 含义 |
|---|---|
| **已锁定** | 按调研推荐值直接实施，不需要再讨论 |
| **待验证后确认** | 方向已定，具体参数由 G1–G4 实测结果决定 |
| **待你拍板** | 需要项目主决定（见 `11-open-decisions.md`） |

> 按你的指示："都按照文中的建议做决策"。因此 T1–T10、P1–P10 全部取调研推荐值并标记为**已锁定**，未做任何替换。

## 一、技术决策（T1–T10）

| 编号 | 决策 | 锁定值 | 何时需要改变 | 落点 |
|---|---|---|---|---|
| **T1** | 画面传输 vs 完整 UI 树重建 | **画面为主，AX / 文本信息为辅** | 只有当自有应用主动接入时才考虑结构化远程渲染 | `02-architecture.md` §1；`04` §8 |
| **T2** | 本地客户端技术栈 | **Swift + AppKit 管窗口与输入；SwiftUI 管设置界面** | 出现跨平台客户端硬要求时再评估；**不因为目标是 Electron 就把 Viewer 也做成 Electron** | `02-architecture.md` §1、§8 |
| **T3** | 网络与媒体底座 | **原生 WebRTC，一对一 + TURN 中继** | 出现"固定经服务器 / 多人观看 / 大量会话管理"时改用 LiveKit 房间体系 | `05` §7 |
| **T4** | 编码方案 | **H.264 硬件链路为基线；HEVC 做对照测试** | HEVC 在两台机器、所选 SDK 与线路上确有画质/码率收益时启用 | `05` §6 |
| **T5** | 单窗口流 vs 大图集 | **主窗口独立流；限制活跃主窗口数量；弹窗不机械地各开一个编码器** | 多窗口编码压力或弹窗兼容性实测表明图集更合适 | `05` §3 |
| **T6** | 尺寸与 Retina | **本地请求尺寸，远端读回实际尺寸；画面与几何携带同一 `layout_version`** | 这是正确性要求，**不建议降级**为长期缩放旧画面 | `05` §5；`03` §1.2 |
| **T7** | 输入与文件传输顺序 | **按键/提交可靠有序；鼠标移动合并；文件限速、独立调度** | 不认为"分几个 DataChannel"就自动解决共同链路拥塞 | `03` §0；`02` §4.3 |
| **T8** | Electron 是否深度接入 | **一期不改包、不依赖调试端口；优先 AX 增强** | 明确接受版本维护成本，或目标是自己开发的 Electron App | `04` §8 |
| **T9** | 扩展方式 | **小型、类型明确的应用适配接口** | 不先做脚本市场、动态插件平台、完整 UI 语义协议 | `02` §7 |
| **T10** | 认证与隐私 | **设备配对、端到端加密、可撤销控制；默认不记录画面与输入内容** | 不作为后续优化项；**不因为自用就开放未认证端口** | `02` §6 |

### 附：三个容易混为一谈的 T 项澄清

**T3 的两个澄清**

1. **TURN 是中继，不是图像处理服务器。** WebRTC 官方将其作为端点不能直连时的常规方案，并列出可自建的 coturn。Apple 平台已有可集成的 WebRTC XCFramework 发行项目，但应固定版本并验证。
2. **"LiveKit 完整 SDK/服务器方案"与"只用原生 WebRTC"不是同一个架构选择。** 采用 LiveKit 时服务器参与媒体转发，需显式配置端到端加密与密钥分发；其信令和 API 元数据不会因此全部对服务器隐藏。

**T5 的澄清**

ScreenCaptureKit 已有 `includeChildWindows`，因此不能照搬旧资料得出"所有子窗口都必须另开一路视频"。**但采集到子窗口 ≠ 本地父子关系、位置、模态行为已解决。**

## 二、产品决策（P1–P10）

| 编号 | 决策 | 锁定值 | 选另一侧会增加什么 | 落点 |
|---|---|---|---|---|
| **P1** | 应用覆盖 | **通用内核；先认证 Claude + 一个原生编辑应用；再用另一个 Electron 编辑器做压力测试** | "所有应用都像本地"会显著扩大兼容性验收，不能只靠多写几个适配器 | `01` §3、`06` §2 |
| **P2** | 中文原生程度 | **认证应用必须在光标附近本地组合 + 候选窗；小面板只作明确降级** | 若完全不允许降级，则 caret 读取失败时应**阻断该应用进入支持列表** | `04` §4.3、§10 |
| **P3** | 编辑边界 | **一期只做输入法本地化；最终编辑状态仍归远端 App** | 完整本地编辑器需要内容/附件/富文本/撤销历史同步，接近另一条产品路线 | `04` §1 |
| **P4** | 文件体验 | **拖入/选择本地文件后显式传输；提供进度与临时文件清理** | 透明文件系统 / 任意文件选择器重定向需要更多系统级集成 | `03` §4；`06` T-FILE |
| **P5** | 应用之外的窗口 | **临时授权相应应用窗口；不自动暴露整桌面** | 不支持外部窗口会使部分登录流程无法闭环；自动整桌面兜底又违背共享范围预期 | `03` §1.3；`06` T-WIN-14 |
| **P6** | 无人值守程度 | **一期保证已登录会话内的重连与应用恢复；其余分别验收** | 首次登录、磁盘解锁、无显示器、合盖不是同一问题，不能合并承诺 | `02` §2 |
| **P7** | 硬件与系统基线 | **先固定一组实际测试设备；能统一到 Apple Silicon 更好** | 旧系统、Intel、混合缩放、不同显示器会增加测试组合 | `06` §2.3 |
| **P8** | 首版外围能力 | **文本/图片剪贴板优先；音频与麦克风按真实使用需要决定** | 双向音频增加权限、回声、设备切换与网络调度工作 | `01` §4 |
| **P9** | 使用与分发方式 | **有商业化可能就先选择许可证边界清楚的依赖，不先整仓 fork 再处理** | MirageKit 的竞品限制、不同项目的源码许可证会直接改变复用路线 | `10-risks-licenses.md` |
| **P10** | 弱网取舍 | **读文字时保清晰度，滚动时争取流畅；优先降帧率，再适度降画质，避免文字长期模糊** | 固定要求高分辨率高帧率就要接受更高带宽或更差线路下明显降级 | `05` §6、§8 |

### P2 与 P3 必须分清

> 你要的是"中文输入法像本地"，**不一定**要求"整个远端编辑器搬到本地"。把两者当成同一件事，项目很容易无意中扩大一倍以上的功能范围。

### 需要写进产品定义的安全边界

**只共享某个窗口 ≠ 给键盘建立了应用沙箱。** 画面与鼠标可限定范围，键盘控制仍是整机语义。专用可信远端 Mac 可以接受单用户会话模型，但**不应宣传为"用户只能影响被共享的应用"**。

## 三、验证门槛（G1–G4，非投票项）

这四项**不该凭感觉选择**，必须用两台真机、固定版本得出结果。

| 编号 | 测什么 | 如何影响选型 | 状态 |
|---|---|---|---|
| **G1** | 文本输入闭环：本地拼音组合、候选窗位置、中文提交、中英混输、选区替换、撤销；尤其**选词 Enter 不误发送** | 决定通用 AX 是否够用，以及是否需要 Claude 专用文本适配器 | ⬜ 未执行 |
| **G2** | 窗口完整性：主窗口、设置、右键菜单、文件对话框、跨应用登录；缩放后真实重排 | 决定逐窗口采集 / 子窗口合成 / 小型图集哪个更合适 | ⬜ 未执行 |
| **G3** | 性能基线：相同画质与像素尺寸下，测采集、编码、解码、呈现、网络、排队；加入延迟与丢包 | 决定 H.264/HEVC、所选 WebRTC 构建是否达标；避免凭名称认定谁快 | ⬜ 未执行 |
| **G4** | 恢复与错误输入：断网、应用重启、窗口切换、权限变化；有无旧点击重放、重复提交、修饰键卡住 | 决定会话状态机能否进入日常使用，而不仅是演示 | ⬜ 未执行 |

### 需要单独说明的一点

**G1 的结论会回写 P2 的可行性。** 若 Claude 只能提供"最后点击位置"级别的插入点信息，则按 P2 的规则，Claude **不得**被标为"本地输入法体验达标"，此时要么开发专用适配器，要么接受降级标识。这不是可以事后放宽的。

## 四、决策的执行规则

1. **已锁定项不需要在开发中重新讨论。** 若认为某锁定值不适用，必须给出实测数据或明确的成本理由，并更新本文件。
2. **G1–G4 未出结果前，不得声称任何能力"已支持"。** 一律使用"待验证"表述。
3. **协议中标记为"冻结"的部分（`03` §7）变更需要更新本文件并说明影响面。**
4. 本文件是 T/P/G 的**唯一权威**；其他文档与本文不一致时，以本文为准。
